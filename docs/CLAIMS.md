# Reliability claims

Every claim points to a test or a recorded measurement. A claim without evidence does not belong here.

| Claim | Evidence | Known limits |
|---|---|---|
| Catalog reports a database outage through `/ready` (503) while `/health` stays 200 | `src/tests/test_health.py`; measured manually in TIK-5 with the database stopped: `/health` 200, `/ready` 503, same result in 3 runs | Clean stop only; a network partition is not tested |
| Catalog recovers from a database outage without a restart | Measured manually in TIK-7: `/ready` back to 200 0.31 s after `docker compose start`, the catalog container kept the same `StartedAt`; no automated test | Requests in flight during the restart still fail; this was not measured |
| The first request after a database restart succeeds | Measured manually in TIK-7, first 10 requests after a restart: all 200 with `pool_pre_ping`, `503 200 200 ...` without it; no automated test | Costs about 0.3 ms per request; a connection that dies during a query still fails with 503 |
| A database outage returns 503, and every error uses the `{"code", "message", "details"}` format | `src/tests/test_error_responses.py`; measured manually in TIK-7: `GET /api/v1/events` returned 503 with the database stopped | Any `OSError` inside a request with a session is reported as a database outage |
| `/ready` answers within `DB__CONNECT_TIMEOUT_SECONDS` when the database host is unreachable | Measured manually in TIK-1: 503 after 5.0 s, and after 1.0 s with the setting at 1; no automated test | Covers connecting only, not a query that hangs on an open connection |
| Every log line of a catalog request carries its `trace_id`, including an unhandled error and its 500 | `src/tests/test_trace_context.py`; measured manually in TIK-8: 30 parallel requests each logged their own id; the uvicorn traceback and 500 line kept the id | The id is not checked for authenticity, only for format; relies on uvicorn running each request in its own task |
| Losing booking's database does not affect catalog | Measured manually in TIK-10: with `booking-db` stopped, booking `/ready` 503 and catalog `/ready` 200; no automated test | Booking does not call catalog yet, so this shows separate databases, not resilience between services |
| A price cannot reference a section of another venue, and a priced event cannot move to another venue | `src/tests/test_section_price_constraints.py` (enforced by composite foreign keys) | Enforced in catalog's database only |
| The catalog contract matches the code, and it documents every status a route returns on purpose | `src/tests/test_contract.py` | 500 and 405 are not documented |
| Models and migrations do not drift apart | `src/tests/test_migrations.py` (`alembic check` in a fresh process) | Alembic does not compare everything, for example check constraints |
| A catalog outage returns 503 in the common error format, and the gateway stays ready | `services/gateway/tests/routing.rs`; measured manually in TIK-12 with catalog stopped: 503 in 0.08 s, `/ready` 200, 200 again after catalog returned, without a gateway restart | Clean stop only; requests in flight when catalog dies were not measured |
| An upstream that does not answer in time gets 504 instead of holding the connection | `services/gateway/tests/routing.rs` | Covers the whole call; a client that sends slowly to the gateway has no timeout yet |
| A trace starts at the gateway and its id is the same in gateway and catalog logs | `services/gateway/tests/logs.rs`; measured manually in TIK-12: the id from the gateway log matched the catalog access line | The id sits at `span.trace_id` in the gateway and at `record.extra.trace_id` in Python, so a query across services needs both paths |
| A path with `..` or `%2e%2e` cannot reach an upstream route the gateway did not match | `services/gateway/tests/routing.rs`; the test fails without the guard | Checked against the `url` crate's normalization only; an upstream that decodes further could still differ |
| A request body over the limit is refused before it reaches an upstream, with or without `Content-Length` | `services/gateway/tests/routing.rs` | The limit is global, not per route |
| A panic in a request does not kill the gateway | Measured manually on axum 0.8.9, one run on macOS: with `panic = "unwind"` the panicking request was dropped and the next one got 200; with `panic = "abort"` the process died. No automated test: test builds always unwind | The client of the panicking request gets a closed connection; stack overflow and out-of-memory still kill the process |
| SIGTERM lets a request in flight finish | Measured manually in TIK-12, one run: SIGTERM 0.5 s into a 2 s upstream call: the client got 200, new connections were refused, exit code 0 after 1.57 s. Idle stop in compose took 0.20 s. No automated test | Docker kills the container after 10 s by default, the same as the upstream timeout, so a request that starts just before SIGTERM may not finish |
| Reused upstream connections do not fail when uvicorn closes them on keep-alive timeout | Measured manually in TIK-12, one run, 60 requests 4.97-5.03 s apart against real catalog: pool idle timeout 90 s gave 2 x 502 (`IncompleteMessage`), 3 s gave none. One 503 in each run came from stopping catalog on purpose and is excluded. No automated test | 60 requests prove little about a rare race; the timeout must stay below every upstream's keep-alive; a connection that dies for another reason still gives 502 |
| Every `/api` route refuses a request without a valid token: missing, forged, expired, unsigned (`alg: none`), another algorithm, another scheme | `services/gateway/tests/auth.rs`; measured manually in TIK-13: 401 without a token, 200 with a token from `issue-token`, `/health` and `/ready` stay public | A token cannot be revoked: a leaked one works until `exp` (at most 15 minutes). A leaked secret lets anyone forge any user. An unknown `/api` path gets 404 without a token, so the route list can be probed |
| A client cannot choose its identity: `X-User-Id` comes only from the token, and upstreams never see the token | `services/gateway/tests/auth.rs`, unit test in `handlers/proxy.rs` for a route without auth | Holds only while upstreams are reachable through the gateway alone. Measured manually in TIK-15: service ports are closed on the host. Inside the Docker network any container can still set any `X-User-Id`, so a compromised service can act as any user |
| The gateway does not start with a JWT secret shorter than 32 bytes | Measured manually in TIK-13: `must be at least 32 bytes for key auth.jwt_secret`; no automated test | Checks length only, not randomness |
| On the same CPU the Rust gateway carries 3.7x the requests of the same proxy in Python, with 4.5x lower p99 at the same load | `infra/benchmark/`, recorded in ADR 0002: 14,733 against 3,943 requests/s on 1 CPU; p99 1.1 against 4.9 ms at 1,970 requests/s; 5 runs each, 16 of 16 behaviour cases match | Docker Desktop VM, load generator on the same machine: only the ratios hold. Through real catalog both reach the same throughput (599 and 596 requests/s), and Rust saves only 0.3 ms at p50 |
| The gateway holds 1,000 connections with a 100 ms upstream on 1 CPU without a failed request | ADR 0002: 9,676 requests/s, p99 112 ms, peak 97 MB, 5 runs | No rate limiting or load shedding yet, so a larger spike is not bounded; memory grows with connections |
| A breaking API change fails CI | `infra/check-contracts.sh`; checked manually in TIK-17: an unchanged contract passes, a removed path fails with "api path removed without deprecation" | On `main` it fails after the commit. It compares schemas only, so a change in behaviour passes |
| The gateway has no known vulnerable dependency | `cargo-deny` in CI; checked manually in TIK-17: advisories ok | Only advisories known to RustSec at the time of the run; only the gateway is checked, Python dependencies are not |
